Cost-guard selectivity sweep, 2026-11-02
========================================

What: core/query TestCostGuardSelectivitySweep (LOGD_SWEEP=1), which sets the cost guard's
thresholds (core/query/costguard.go). Per corpus and selectivity: the share of pages and of
I/O units (8-page compressed blocks, or pages when uncompressed) the candidates touch, the
guard's decision, and the median of 5 timed runs (after 1 warm-up) of the index path with
the guard switched off and of the forced scan, at limit=100, limit=1000 (backward) and
unbounded ("all rows"). s/i = scan time / index time: above 1 the index path is faster.

Corpora: 200,000 records in ONE sealed segment ("GET /api/v1/orders/<i> 200 took <ms>ms
trace_id=..."), query {app="bench"} | latency_ms > T. Scattered = hashed latency, matches
spread evenly over every page; clustered = latency falling with the record number, so the
matches are the OLDEST records, contiguous at the start of the segment.

Machine: Intel i5-1145G7 (4 cores / 8 threads), 15 GB, NVMe ext4, Linux 6.12, Go 1.26.2.
Data on a real disk (LOGD_BENCH_DIR=$HOME/.cache/logd-bench; /tmp is tmpfs).

LOAD CAVEAT: the machine was shared with other agents running builds and tests; the load
average was 5.5-8.9 on 8 threads throughout (logged at the start and end of every run), and
the author's own test runs overlapped parts of runs 1 and 3. Single cells vary by up to
~2x between runs (see the min-max columns below); the conclusions rest only on patterns
that hold in every run.

Runs:
  run 0  01:01-01:05  preliminary, limit=100 and unbounded only (before the limit=1000
                      column was added); guard column = provisional fixed-ratio rule.
  run 1  01:08-01:15  full sweep; guard column = provisional rule (candidates > 20 x limit
  run 2  01:15-01:21  AND units > 90%), kept from the earlier uncommitted rework.
  run 3  01:22-01:28  full sweep with the COMMITTED rule (guard column = that rule).
  run 4  01:52-01:59  the committed rule again, on the final code: after the planner
                      began intersecting candidate sets smallest-first, which made the
                      index path cheaper. Lower load (2.6-4.5). Every cell the rule scans
                      had the scan faster (s/i 0.09-0.88); every cell it keeps had the
                      index faster, but for two ties at the threshold (0.99, 1.03-1.05).
                      Not in the variance table above, which covers runs 1-3.

Committed rule (from runs 1 and 2, confirmed by run 3): a bounded query scans a segment
instead of fetching by offset iff
    candidates > 1.0 * sqrt(limit * records_in_segment)   (here 4,472 at limit=100,
                                                            14,142 at limit=1000)
AND candidates cover > 90% of the segment's I/O units.
An unbounded query never scans for the guard.

Findings (ranges from runs 0-3; run 4, at a lower load, had the same pattern with
the index path up to ~140x faster in the most selective cells):
  - Unbounded: the index path is faster in EVERY cell of every run, 2.6x-74x. Never trip.
  - Clustered (<=50% of units): the index path is faster in every cell, 2.2x-74x, at both
    limits; a backward scan must decode the whole newer part before its first match.
    So coverage must be high before scanning can pay.
  - Scattered (100% of units): the scan wins at high selectivity for bounded queries, by
    up to 2x compressed and 11x uncompressed at limit=100 — the guard is worth keeping.
    The crossover, in candidates:
                      limit=100       limit=1000
        compressed    ~5k-10k         ~10k-20k
        uncompressed  ~4k-10k         ~20k
    It moved ~2-3x for a 10x limit. sqrt(limit*n) predicts 3.2x (4.5k -> 14k); a fixed
    over-fetch ratio predicts 10x: fitted at limit=100 (~50x), it would put limit=1000's
    crossover at ~50k, where the scan already wins 1.3-1.5x (compressed) and 3-5x
    (uncompressed).
  - With the committed rule, the worst measured miss (median over runs 1-3) is the
    compressed 2% cell at limit=100: kept on the index at s/i 0.86, i.e. the scan would
    have been 1.16x faster. Every tripped cell has median s/i <= 0.94.

Variance across runs 1-3: scan/index time ratio per cell (>1 = the index path is faster),
as median [min-max]. "rule" is what the committed rule decides for that cell at that limit
(trip = scan): candidates > sqrt(limit * 200000) AND units covered > 90%.
